How the Teensy, XIAO & K230D work as one system

A top-to-bottom map of the rescue robot's brain. The Teensy 4.1 is the conductor: it pulls in pre-chewed data from two smart co-processors (the XIAO ESP32-S3 camera and the K230D AI processor) plus its own onboard sensors, fuses and filters everything, decides which behaviour to run, and finally drives four wheels. Read top to bottom — each section zooms one level deeper.

1 · The whole robot at a glance

Everything the Teensy reads is already simplified by the time it arrives. The XIAO does the heavy camera vision and hands over a few bytes; the K230D runs a YOLO model and hands over bounding boxes. The Teensy never touches raw pixels — it works with small, fast messages.

Key idea: the Teensy is not doing image processing. The XIAO and K230D are offloaded brains that pre-digest the camera into tiny messages. This keeps the Teensy's control loop fast and deterministic.

2 · The 5-layer architecture

All firmware lives under src/<layer>/. The rule is strict: calls only flow downward. A layer never calls a layer above it. This is what keeps the "spaghetti" out — each box below only knows about the box beneath it.

actions/
Blocking motions you call and wait on: Turn::turn(180,60), Forward::forward(60,35), Drive::runLinePID().
processing/
Turns raw bytes into meaning: a confirmed command code, a line error, a victim direction, a pose.
sensors/
Just moves bytes in/out. XIAO_link::get(reg) / send(reg,val). No interpretation.
drivers/
Per-chip register code (the "yache" wrappers). Speaks the actual chip language.

Adding new code? A new chip → drivers/. Reading raw bytes → sensors/. Decoding/fusing them → processing/. A motion primitive → actions/. A new behaviour → state_machine/.

3 · The main loop — one pass, every cycle

STS-imuMerge.ino → loop() is deliberately tiny. It runs the same 4-step pipeline forever: pump I/O → process → handle debug → run the active state.

loop() {
  Sensors::XIAO_link::tick();  // 1 — drain RX into register cache
  Processing::XiaoDecode::tick(); // 2 — read cache, vote, expose lineError/command
  while (Serial.available()) Mapping::handleSerial(...); // 3
  StateMachine::tick();         // 4 — act
}
Why two steps per sensor? Step 1 (sensors/) only moves bytes — fast, non-blocking. Step 2 (processing/) interprets them. Splitting them means the transport never blocks on decode logic, and decode always works on the freshest cache.

4 · The XIAO ESP32-S3 path primary vision input

The XIAO runs the camera and boils each frame down to a handful of registers. Communication is a tiny register protocol over UART3 at 4 Mbps using YacheEncodedSerial — a 3-byte packet [255, reg, value].

The register protocol

RegisterIDDirectionMeaning
XIAO_REG_FEATURE0x01Xiao → TeensyDetected feature byte (green, silver, intersection…) — the noisy raw vote
XIAO_REG_COM0x02Xiao → TeensyLine centre-of-mass, 0..254 (127 = centred) — the steering error
XIAO_REG_MODE0x03Teensy → XiaoTells the XIAO which vision program to run (see below)

Teensy steers the XIAO's "mode"

The Teensy can re-task the camera by writing XIAO_REG_MODE. This is the one upward message — the state machine swaps the camera's job to match the behaviour it's running.

0 · LINE
Follow the black line, watch for green/silver/intersection glyphs.
1 · EVAC
Evacuation-zone vision.
2 · NOGI
No-green-intersection disambiguation (which arm of the cross to take).

Two speeds on purpose. lineError (steering) is time-critical, so it's read raw every loop. The FEATURE byte is noisy, so it's only trusted after surviving a vote — see next section.

5 · CommandFilter — turning noisy glyphs into trusted commands

A single camera frame can lie (motion blur, glare). So the raw FEATURE byte is never acted on directly. Instead, every value drops into a 15-slot ring buffer, and a command is only "confirmed" once it collects enough votes. Different events need different thresholds — a U-turn must be very sure; a line-loss can react faster.

Clever bit: the U-turn glyph (code 1) also counts as one vote toward both left and right, so a normal single-side green approach can never accidentally cross the U-turn threshold. Precedence: silver → u-turn → green → intersection → no-line.

6 · The K230D AI path victim detection

The K230D is a dedicated AI processor running a YOLO model. It streams bounding boxes over UART8 at 115 kbps. The Teensy sends it a 1-byte command every 100 ms — 0x00 idle or 0x01 detect — and parses the frames that come back.

Wire format (binary frame)

[0xAA][0x55][COUNT] ( [CLS][SCORE][X1hi][X1lo][Y1hi][Y1lo][X2hi][X2lo][Y2hi][Y2lo] ) × COUNT [CHKSUM]

Each box = 10 bytes (class, score, and a hi/lo bounding rectangle). CHKSUM = XOR of every byte from the 0xAA header through the last box byte. Frame parsing lives in processing/K230Decode; the sensors/K230_link layer just buffers bytes and never understands framing.

7 · Onboard sensors — IMU · ToF · Touch

Beyond the two camera co-processors, the Teensy reads three local sensors directly. These feed slope compensation, evac-zone mapping, and contact sensing.

🧭 IMU (MPU6050)

I²C. yacheMPU6050 driver → Sensors::IMU. Provides pitch / roll / yaw. Pitch can bias the wheel mix on slopes (WeightDistribution table); yaw feeds the EVAC pose/EKF.

📏 ToF (VL53L7CX)

I²C multi-zone distance array. yacheVL53L7CX driver. Used in the evacuation zone for wall ranging → Pose/EKF → Mapping (a 40×40 grid).

👆 Touch + conductive

GPIO. Front bumper and conductive probes are still available to states that need contact sensing, especially evacuation behaviours.

8 · The state machine — choosing a behaviour

The robot is always in exactly one state. Each state is a namespace with onEnter() + update(). StateMachine::tick() dispatches to the active state every loop; a state requests a change with transitionTo(NEXT), which is applied at the start of the next tick (and fires the new state's onEnter()).

9 · Inside LINE_Follow — priority dispatch

10 · From line error to four wheels — the PID

When no command fires, Drive::runLinePID() converts the XIAO's line centre-of-mass into a left/right speed split. A background 9 ms IntervalTimer ISR then streams the four wheel gains to the STS servos — control math and the servo write are decoupled.

Why asymmetric?
The L (×0.65) and R (×1.3) correction scales were hand-tuned: on a left-up/right-down sideways slope, making the lower side more aggressive (and allowing negative speed) tracked the line far better.
Why a 9 ms ISR?
The servo bus write happens on a timer, not in the main loop. motor() just updates four volatile gains; the ISR pushes them at a steady rate so wheel output never stutters when the loop is busy.
Slope / tilt comp
An optional path (imuCompensation + WeightDistribution table) scales the unloaded wheels by IMU pitch. Present but off by default in flat-line follow.
