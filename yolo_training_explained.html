What is YOLO?

YOLO (You Only Look Once) is a family of object detection models. Unlike older two-stage detectors, YOLO does the whole job in one forward pass through a convolutional neural network:

  • Input: a single image (e.g. 640×480 RGB).
  • Output: for every object it finds — a bounding box (x, y, width, height), a class label, and a confidence score.

YOLOv8 (Ultralytics) is the version used here. The "n" in yolov8n stands for nano — the smallest variant, chosen so it fits in the K230D's limited RAM.

Step 1 — Collect Images

Take photos of the objects you want to detect, in the same conditions the deployed model will see: same camera, same lighting, same angles, same backgrounds.

  • Aim for at least 100–300 images per class for a small custom model.
  • Include hard cases: partial occlusion, weird angles, motion blur, different lighting.
  • Avoid using images from the internet unless they truly match your deployment environment — the model will overfit to the wrong distribution.

Step 2 — Label the Images

For every image, you draw a bounding box around each object and assign it a class. Tools commonly used: Label Studio, Roboflow, CVAT, labelImg.

YOLO's label format is one .txt file per image, one line per object:

<class_id> <x_center> <y_center> <width> <height>

All four numbers are normalised to [0, 1] relative to image size.

Example (image contains one "silver" object at index 1):

1 0.512 0.488 0.213 0.302
Important: the class IDs you assign here are the same IDs your deployed code reads. If your data.yaml says 0: black, 1: silver, then the inference labels list must be ["black", "silver"] — in that order. Swapping them is the #1 source of "label is wrong" bugs.

Step 3 — Split & Configure (data.yaml)

Split your labelled dataset into three folders:

  • train/ — ~80% of images, used to update model weights.
  • val/ — ~15%, used after each epoch to measure progress on unseen data.
  • test/ — ~5%, held back for the final evaluation.

Then describe the dataset in a YAML file YOLO can read:

path: /datasets/rescue_line
train: images/train
val: images/val
test: images/test

nc: 2
names:
  0: black
  1: silver

Step 4 — Train

Training adjusts millions of weights inside the neural network so its predictions match the labels. It works by:

  1. Forward pass: push a batch of images through the network, get predicted boxes.
  2. Loss: compare predictions to ground-truth labels — a single number measuring how wrong the model is (combines box-position error, class error, objectness error).
  3. Backward pass: compute gradients — for each weight, "how should I change you to reduce the loss?"
  4. Update: the optimizer (SGD/AdamW) nudges every weight slightly in the right direction.
  5. Repeat for every batch in the dataset. One full sweep = one epoch.

Example invocation (this project uses train_yolov8n.py):

python train_yolov8n.py \
    --data data.yaml \
    --epochs 100 \
    --batch 16 \
    --img-height 480 --img-width 640

Key training concepts

TermMeaning
EpochOne full pass through the training set.
Batch sizeHow many images go through the network at once. Bigger = smoother gradients, more GPU memory.
Learning rateHow big a step the optimizer takes. Too high = unstable; too low = never converges.
Pretrained weightsStart from yolov8n.pt (already trained on COCO). Much faster than training from scratch.
AugmentationRandomly flip/rotate/colour-shift images each epoch so the model generalises better. Configured by hsv_h, fliplr, mosaic, etc.
AMPAutomatic Mixed Precision — uses float16 where possible to speed up GPU training.

Step 5 — Validate

After training, the script runs the best checkpoint against the validation set and reports:

  • mAP50 — mean Average Precision at IoU ≥ 0.5. The "easy" detection metric. Aim for > 0.7 on a clean dataset.
  • mAP50-95 — averaged over IoU thresholds 0.5 to 0.95. Strict; rewards tight boxes.
  • Precision — of the boxes you predicted, how many were correct.
  • Recall — of the objects that existed, how many you found.
Reading the curves: training loss should drop steadily. If validation loss starts rising while training loss keeps dropping, you're overfitting — the model memorised the training set. Fix: more data, more augmentation, fewer epochs, or smaller model.

Step 6 — Export to ONNX

The .pt file is a PyTorch artifact. To deploy on most hardware (including the K230D toolchain), it needs to be converted to ONNX — a portable, framework-agnostic graph format.

python export_to_onnx.py best.pt \
    --img-height 480 --img-width 640 \
    --opset 11

The exporter also runs onnxsim which fuses redundant operations — smaller, faster, and easier for downstream compilers to handle.

Step 7 — Quantize to .kmodel

The K230D's KPU (neural-network accelerator) runs integer math, not float. Quantization converts every weight and activation from float32 to int8/uint8, shrinking the model ~4× and making it many times faster — but introducing some accuracy loss.

This is done by convert_to_kmodel3.py using nncase:

python convert_to_kmodel3.py best.onnx \
    --calib-data ./calib_images \
    --num-samples 200 \
    --quant-type uint8 \
    --w-quant-type int8 \
    --calib-method NoClip

What is calibration?

To pick good integer scales, nncase needs to know the typical range of values flowing through the network. You give it ~100–500 representative images (the calibration set), it runs them through the float model, observes the activations, and chooses quantization parameters.

Calibration matters a lot. If your calibration images don't match the deployment environment, activation ranges are wrong, quant scales are wrong, and confidence scores collapse — even though boxes still appear in roughly the right places. This is the most common cause of "detection works but confidence is low".

Step 8 — Deploy

Copy the .kmodel onto the K230D (e.g. /data/kmodel/best_640x480_k230.kmodel) and load it from your CanMV script:

from libs.YOLO import YOLOv8

yolo = YOLOv8(
    task_type="detect", mode="video",
    kmodel_path="/data/kmodel/best_640x480_k230.kmodel",
    labels=["black", "silver"],           # MUST match data.yaml order
    model_input_size=[640, 480],
    rgb888p_size=[640, 480],
    conf_thresh=0.3, nms_thresh=0.45,
)

Improving K230D Accuracy & Performance

Key points to recover confidence lost to quantization, in order of payoff:

  • Use int8 for weights (--w-quant-type int8) — biggest free win.
  • Try every calibration method (Kld, NoClip, AbsMax) and keep the best.
  • Calibration images must come from the actual K230D camera in real deployment lighting. This matters more than any flag.
  • Use 200–500 calibration images, not 20.
  • Check the float model first. Run best.pt on real frames — if float confidence is already low, the problem is training, not quantization.
  • More & better training data: hard negatives (no-object frames, look-alikes), tight labels, images from the deployment camera.
  • QAT (Quantization-Aware Training) if PTQ tuning isn't enough — fine-tunes the model to be quantization-robust. Big accuracy gain, but requires retraining.
  • Smaller input (e.g. 320×320) for ~4× speed-up if fine detail isn't needed.
  • Stick with yolov8n — larger variants don't fit comfortably.
  • Preprocessing must match between calibration and deployment: resize method, RGB/BGR order, value range.
  • Raise conf_thresh to 0.25–0.4 in production. 0.03 is a debug value.

Summary

Training a YOLO model is a pipeline: collect → label → split → train → validate → export → quantize → deploy. Each stage can degrade quality independently — so when something looks wrong, identify which stage is responsible before changing things.
