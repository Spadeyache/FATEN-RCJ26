Evac-Zone Mapping — How It Works Now

Teensy firmware · src/processing/ · snapshot of current behaviour (not yet driven)

Status today: the full mapping pipeline is built and wired, but it runs passively. In EVAC_Search the robot stays parked (Drive::stop()) and only beeps at 1 Hz while the map fills from ToF + IMU. Nothing yet reads the occupancy grid to plan motion — that is the "run the map" Phase 2 work. This page documents the machinery that already exists.

1 · The big picture

A single orchestrator, Processing::Mapping, fuses dead-reckoning, IMU yaw, and time-of-flight ranges into a 3-state pose EKF and a 40×40 occupancy grid. It self-corrects when stuck (scan-matching) and checkpoints to EEPROM so a mid-run reset can resume.

Pose EKF

3-state (x, y, θ) Kalman filter. Predict from motor command, correct from IMU yaw.

MapGrid grid

40×40 cells @ 30 mm. Per cell: log-odds occupancy + a semantic label.

Recalibrate recovery

Stuck detector + ToF↔map scan-match snap to fix accumulated drift.

MapPersist EEPROM

Diffed, wear-minimised checkpoints of the semantic map + pose snapshot.

2 · What one tick() does

Called every loop while in EVAC_Search (Mapping.cpp:170). Order matters:

1

posePredict

Read averaged motor gains → unicycle (v, ω), integrate over dt. Covariance grows.

2

poseUpdateYaw

Fuse IMU yaw (Madgwick), de-biased against the θ=0 snapshot taken at init().

3

tofPoll

Each ready ToF zone → world-frame ray → integrate into grid; cache valid rays for scan-match.

4

maybeRecalibrate

If stuck & ≥4 rays, grid-search a pose snap; accept only if it clearly beats the seed.

5

maybeCheckpoint

Every 30 s, if ≥60 cells changed, diff-write the semantic map to EEPROM.

3 · Pose estimation (the EKF)

Pose.h / Pose.cpp — state is (x_mm, y_mm, θ) with a 3×3 covariance P.

StepSourceEffect
posePredict(v, ω, dt)Commanded motor gains (no encoders yet) Moves the estimate forward; inflates covariance (uncertainty grows with motion).
poseUpdateYaw(θ_meas)IMU yaw, Madgwick fused Pulls θ toward the measurement; shrinks heading covariance.
poseUpdateWall(...) Phase 2ToF wall geometry Declared but not yet called — intended x/y wall-snap correction.

Velocity comes from readMotorCommand(): it averages the four wheel gains into left/right speeds, converts via FORWARD_MS_PER_MM, and derives ω = (vR − vL) / WHEELBASE_MM (140 mm). So odometry is open-loop motor-command based — a known weak point the scan-match step exists to patch.

4 · The occupancy grid

MapGrid.{h,cpp} — two parallel 40×40 = 1600-byte arrays:

ArrayMeaning
logodds[] (int8)Occupancy belief, clamped [−64, +64]. Negative = free, positive = occupied.
semantic[] (uint8)A CellSemantic label (unknown / free / wall / obstacle / evac corner / victim).

Frame: world origin (0,0) ↔ cell (0, 20). +x = forward into zone (column), +y = robot's left at entry (row). 30 mm cells → a ~1.2 m square zone.

Ray integration

mapIntegrateRay() walks a Bresenham line from the sensor to the hit point:

  • cells along the way get LO_MISS (−2) → drift toward free
  • the endpoint, if a real hit, gets LO_HIT (+6) → toward occupied
  • crossing ±LO_DECISIVE (30) promotes the semantic label (FREE / WALL), respecting a rank so a victim is never overwritten by "free".

Semantic rank (higher wins)

victim-alive 7 > victim-dead 6 > evac-corner 5 > obstacle 4 > wall 3 > free 2 > unknown 1. Equal rank overwrites (re-detections refresh).

5 · Drift recovery (Recalibrate)

Recalibrate.{h,cpp} compensates for open-loop odometry drift.

StuckDetector

Arms when commanded to drive (≥30 mm/s). If the pose moves <5 mm for 1000 ms, it fires once — "we think we're driving but we're not moving."

scanMatchPose

3-D grid search over Δx, Δy, Δθ (±60 mm / ±10°) around the current pose. Each candidate's cached rays are re-projected and scored against the semantic map.

Accept gate

The best candidate is adopted only if its margin over the seed score ≥ 4. On accept, pose snaps and covariance is re-inflated modestly.

Scoring rewards rays that land on obstacle/evac (+2) or wall (+1), penalises free cells and out-of-bounds (−1). It rewards alignment with already-mapped structure.

6 · Persistence (MapPersist)

MapPersist.{h,cpp} — EEPROM layout from 0x0020:

RegionSizeNotes
MapHeader40 Bmagic, version, pose + P-diagonal, flags, run_count
semantic[1600]1600 Bthe label map only (log-odds is rebuilt live)
crc324 Bover header + semantic, for validity check on load

A RAM shadow of the last-saved array drives byte-level diffing — only changed bytes are EEPROM.update()'d, minimising flash wear. On restart-load the semantic map is kept but logodds is cleared and pose covariance inflated, so old structure guides scan-match while fresh sensor data re-confirms occupancy.

8 · What's not implemented yet (the "run the map" gap)

Exploration planner

Nothing consumes the grid to choose where to drive. EVAC_Search keeps the robot parked. This is the core of "running the map".

Victim / corner fusion

K230Decode::detections() are streamed but not yet written into the semantic grid as VICTIM_* / EVAC_* cells.

Wall-snap EKF update

poseUpdateWall() is declared but never called — x/y is still open-loop between scan-match snaps.

Deploy / exit logic

EVAC_Deploy and EVAC_Exit are skeletons; no map-driven navigation to drop points or the exit.
