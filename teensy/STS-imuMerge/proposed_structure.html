STS-imuMerge — proposed code structure

Four layers, strict downward dependencies. Each existing file is mapped to one layer; cross-layer leaks are flagged.

The four layers

STATE MACHINE  Policy. What the robot should be doing right now.
Owns RobotState and state transitions. Reads sensor facts, decides actions, never touches hardware directly.
▼ calls
DRIVERS & WRAPPED ACTIONS  Verbs. "Turn 90°", "drive 200 mm", "grab".
Composite actions on top of bare drivers. No knowledge of why they're being called.
▼ reads
PROCESSING & DATA FILTERING  Facts. Smoothed error, voted command, fused pose, occupancy.
Stateless-where-possible math on top of raw sensor bytes. PID, EMA, vote filter, EKF, scan-match, log-odds.
▼ subscribes to
COMMUNICATION  Bytes. XIAO, K230D, IMU, ToF, STS bus, KRS bus.
Owns every UART/I²C transaction. Exposes raw values + parsed frames. No policy, no smoothing.

Where each existing file lands

COMMUNICATION

  • Comms.ino — XIAO register pump + K230D frame parser (split: parser → K230Link.cpp)
  • yacheEncodedSerial.{h,cpp} — XIAO register protocol
  • yacheSTS.{h,cpp} — STS motor bus protocol
  • yacheMPU6050.{h,cpp} — IMU I²C reads (see leak ↓)
  • yacheVL53L7CX.{h,cpp} — ToF I²C reads
  • IcsClass_V300/ — KRS smart-servo bus
  • Sensors.ino (read side) — touch / conduct digital reads

PROCESSING & DATA FILTERING

  • CommandFilter.h — rolling vote filter on XIAO feature IDs
  • Drive.ino :: runLinePID() — PID + EMA on line error (extract → LinePID.cpp)
  • Pose.{h,cpp} — EKF predict / yaw update
  • MapGrid.{h,cpp} — log-odds occupancy integration
  • Recalibrate.{h,cpp} — scan-match + stuck detector
  • MapPersist.{h,cpp} — dirty-cell tracking
  • Mapping.ino — orchestrates the per-tick pipeline
  • IMU EMA smoothing (currently inside yacheMPU6050 — see leak ↓)

DRIVERS & WRAPPED ACTIONS

  • Drive.ino :: motor() + ISR — atomic 4-wheel gain write
  • Actions.ino :: executeTurn / doUTurn — timed turn primitives
  • Actions.ino :: execForward — open-loop and yaw-hold drive-N-mm
  • Actions.ino :: grabARM / liftARM — servo + KRS wrappers
  • Sensors.ino :: updateSensors() — driver-facade read tick

STATE MACHINE

  • STS-imuMerge.ino :: loop() — state dispatch
  • globals.h :: RobotState — enum + transition flags
  • Actions.ino :: handleTurnTick (belongs here — see leak ↓)
  • Actions.ino :: handleEvacuationZone (belongs here)
  • Actions.ino :: enterEvacuationZone (belongs here)

Per-tick data flow

loop() {                                                       SM
    comms::pollAll()       // XIAO bytes, K230 frames, ToF, IMU  COMM
    processing::tick()     // filter votes, PID error, EKF, map  PROC
    stateMachine::step()   // pick action from current state     SM
        └─ actions::executeTurn() / motor() / grabARM() / ...    DRV
}

One direction. SM never reads a raw byte. DRV never decides which turn to make. PROC never writes to a motor. COMM never knows what state the robot is in.

Current leaks worth fixing

Leak 1 — State logic inside Actions.ino. handleTurnTick, handleEvacuationZone, and especially enterEvacuationZone (with its nested while(!touchfront) blocking loops and while(true){} at the end) are policy, not verbs. They belong in state/. The action layer should expose liftARM, grabARM, execForward — the evacuation choreography is then a state-machine script composed of those verbs.
Leak 2 — Touch/conduct policy inside loop()'s FOLLOWING_LINE case. STS-imuMerge.ino lines 103–133: a 30-line touch-reactive sub-routine sits inline in the state dispatch. This is a separate sub-state ("touched, escaping wall"). Either model it as a real state, or move the body into state/FollowingLine.cpp as a private helper.
Leak 3 — PID inside Drive.ino. runLinePID() is pure processing (reads filtered error → writes motor()). It lives alongside the ISR purely for historical reasons. Move to processing/LinePID.cpp; Drive.ino keeps only the bus/ISR/motor() primitive.
Leak 4 — EMA smoothing inside the IMU driver. Smoothing in yacheMPU6050.cpp means the driver is no longer "raw bytes." If two callers ever want different smoothing windows, you'll have to add a flag. Cleaner: driver returns raw; processing/ applies EMA per consumer.
Leak 5 — globals.h is a god-header. Every .ino includes it, so every file pulls in Servo.h, arm_math.h, IcsHardSerial, STS, and every extern. Split per layer (comm_globals.h, proc_globals.h, …) so a comms file can't accidentally reach into robotState.
Leak 6 — Blocking delay() calls in actions. liftARM sleeps 800 ms; enterEvacuationZone chains delay(200) + while loops. While these block, updateComms() stops running and the XIAO ring buffer can overflow. Either pass an updateCallback into the action, or convert the choreography to a step-driven sub-state.

Layer rules of thumb

LayerMay callMust not
SM actions/*, processing/* (read), comms/* (read facts only) read raw UART bytes; call _sts.power(); do PID math inline
DRV comms/* (write bytes), processing/* (read e.g. yaw) read robotState; change robotState
PROC comms/* (read raw values) call motor(); read/write robotState
COMM HAL (Wire, Serial, pinMode) know about robot state, smoothing, PID, or actions

Migration order (low-risk first)

  1. Split globals.h into four per-layer headers. Pure include-graph cleanup, no behaviour change.
  2. Extract runLinePID() from Drive.ino → processing/LinePID.cpp.
  3. Move handleTurnTick / handleEvacuationZone / enterEvacuationZone from Actions.ino → state/.
  4. Lift the touch/conduct block out of loop() into state/FollowingLine.cpp.
  5. Extract K230D parser from Comms.ino → comms/K230Link.cpp.
  6. Move IMU EMA out of yacheMPU6050.cpp into processing/.
  7. Replace blocking delay()s in the evac sequence with a step-driven sub-state.

Each step is independently testable on the actual robot — no big-bang rewrite required.
