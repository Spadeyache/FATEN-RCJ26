Fixing PTQ YOLOv8n on the Kendryte K230D

A multi-day investigation into a quantized object detector that looked broken, several wrong turns about preprocessing, a stale eval that turned out not to be the script it appeared to be, and a vendor post-processing helper that silently read bounding-box coordinates as class scores. Written up so the next person doesn't repeat the same mistakes.

Setting

Where we started.

This work sits inside k230-train/ — the Post-Training Quantization (PTQ) pipeline for the team's RescueLine vision model. The model is a YOLOv8n object detector with two classes: silver and black (the two kinds of victim markers the rescue robot has to find). The training data are 640×480 grayscale photos that have already been contrast-stretched with histogram equalization and then stored as 3-channel JPGs (every pixel has R=G=B).

The Kendryte K230D is the target chip — a small embedded SoC with a neural-network accelerator (the KPU). To get a YOLOv8 model onto the KPU you compile the ONNX export down to a .kmodel file using nncase inside a Linux container, choosing a quantization strategy: which calibration metric, which activation/weight bit-widths. Each of those knob combinations is what we call a variant.

The user's specific ask at the start of the session was to compile a new variant with KLD calibration, uint8 activations, uint8 weights, 640×480, using the 74-image calibration set, and to compare it to the float reference on a single test image. That ask grew into the investigation written up below.

Phase 1Initial compile (KLD u8/u8, calib_74)

Getting the Docker environment to a point where a kmodel could come out the other end.

What we thought
Compiling would be a one-liner inside the user's existing k230-nncase Docker image — it already has nncase 2.9.0 and nncase-kpu installed.
What we tried
Brought the container up via docker compose up out of C:\Users\magic\Documents\robocup\k230\. The compose file mounted that directory but not the k230-train repo. We extended the compose to also mount k230-train at /k230-train and the YOLO dataset directory at /datasets (read-only).
What we found
The image was missing opencv-python and pyyaml needed by src/convert/convert_kmodel.py and the variant runner. We installed those with pip into the running container (headless OpenCV, to avoid GL dependencies). The KPU simulator binary nncase.simulator.k230.sc was on disk under /usr/local/lib/python3.10/dist-packages but not on PATH; we exported the directory so the Python nncase.Simulator wrapper could shell out to it.
What we changed
Added a new entry yolov8_kld_u8u8_calib74 to configs/variants_quant.yaml with the requested settings, then ran batch_export.py --only yolov8_kld_u8u8_calib74. First successful compile in about 98 seconds. Output kmodel 3.09 MB.

Phase 2First float-vs-PTQ comparison

Where the symptom that drove the rest of the session showed up.

We ran the new kmodel and the existing yolov8_existing_float reference through the nncase.Simulator on the same image (c27f5e94-2s1b_0031.jpg from the calibration set, picked because the filename pattern 2s1b meant two silver markers and one black). The float reference produced a smooth distribution of confidence scores — top-1 at 0.824, top-2 at 0.823, top-3 at 0.765, then a sharp drop to noise. The new PTQ kmodel produced something stranger:

RankFloat scorePTQ score
10.8240.686
20.8230.686
30.7650.686
4–100.06 and below0.686 (all)

Every confident PTQ detection was sharing the same score — 0.686 exactly. That number has no semantic meaning; it's just one of the 256 levels available in a uint8 dequant scale. Localization was fine; ranking was destroyed. With every score tied, non-maximum suppression's "keep the highest" rule degenerates into "keep whichever box NMS sees first," and on a device with a fixed CONF_THRESHOLD you either keep every confident anchor or none.

Score saturation, not localization failure. The detector still knew where the objects were; it had lost the ability to say how sure it was.

Phase 3Was preprocessing inconsistent?

The first hypothesis we tested — and ruled out.

What we thought
The calibration step has to feed the kmodel data in the same distribution it will see at runtime. If the kmodel's preprocess mode (raw_01, divide-by-255 only) didn't actually match what the Ultralytics ONNX export expects, the calibrated activation ranges would be wrong and could explain the collapsed scores.
What we tried
Loaded the ONNX directly with onnx and inspected the first ops. The graph starts with a plain Conv on a float32 (1, 3, 480, 640) input — no Div(255), no Sub(mean) baked in. That is the standard Ultralytics export: it expects the caller to divide by 255 before feeding the model. The kmodel was compiled with preprocess_mode=raw_01 which bakes exactly that /255 into the model. Calibration loaded uint8 RGB CHW images and nncase did the dequant internally. So calibration and runtime see the same distribution as the original ONNX.
What we found
Preprocessing was consistent. The score collapse had to be coming from somewhere else.
What we changed
Nothing. Moved on.

Phase 4Sweep across all kmodels

Establishing that the collapse was a property of u8 activation, not of this particular variant.

We built a small annotation script, src/eval/draw_yolov8_boxes.py, that runs an arbitrary kmodel on an image, draws post-NMS boxes on the letterboxed canvas, and writes a JPG. We ran it across every yolov8 kmodel in exports/, on two images: one that was in the calibration set, one that wasn't. The results were illuminating:

kmodelTop score (all images)
yolov8_existing_float0.49 – 0.85, smooth
yolov8_existing_mix0.5034 (uniform)
yolov8_existing_squant0.5034 (uniform)
yolov8_squant_raw01_calib1280.5034 (uniform)
yolov8_kld_u8u8_calib74 (new)0.6860 (uniform)

Every PTQ kmodel was finding the right boxes (within a few pixels of the float reference) on every image — but each one had ground all its confident detections to its own characteristic ceiling. The old calibrations landed at 0.5034; ours at 0.6860; both are quantization grid lines, not confidences.

This made the eval_summary.json files stored next to those older kmodels look suspicious — they claimed recall = 0.0 and avg_best_iou = 0.0, but when we rendered them on the same images they were finding the objects with IoU around 0.85.

Phase 5Comprehensive diagnostic + int16 fix

Quantifying the failure mode and proving int16 activations restore the score distribution.

We wrote src/eval/diagnose_yolov8_quant.py: for each (kmodel, image) pair it records the raw max class score, the top-20 boxes pre-NMS, post-NMS survivors, count of detections above 0.1/0.3/0.5, the number of distinct scores in the top 20, and best-IoU vs each ground-truth box. It also writes an annotated JPG with GT in green and predictions in class color.

We then ran it across 13 images (2 in calib_74, 11 not in it but labelled) and all six kmodels. The "distinct top-20 scores" column made the failure mode obvious:

Image float mix squant squant128 u8u8 calib74 i16act
003a746b20699920
0148e2fc20145518
0358804218477720
03cb186920251318
c27f5e9420325519

Float and the int16-activation variant both keep most of the top-20 scores distinct. Every u8-activation variant collapses to between 1 and 9 distinct values — sometimes just one.

That was enough to commit to the fix. We added one more variant to variants_quant.yaml — yolov8_kld_i16act_u8w_calib74 — identical to the u8/u8 variant except activations are int16 instead of uint8. Compiled it (~62 s, 3.35 MB). Fresh pc_eval_yolov8.py across 20 validation images:

yolov8_existing_float0.8010.7280.97
yolov8_existing_mix0.7920.7160.97

The int16-activation variant matches float on every metric, and in fact beats it slightly on average best IoU (within noise — both sample from the same 20-image set). This was the model we picked to deploy.

Full writeup of this phase lives in YOLOV8_K230_QUANT_DIAGNOSIS.md.

Phase 6Forensic chase of the stale eval

Why did the OLD eval_summary.json say zero recall when the model is fine?

Before deploying the new variant the user wanted closure on the old eval files that had triggered the original concern. We needed to know whether the old "recall = 0" had been a real failure that the new variant fixed, or a measurement bug that had misled everyone.

What we thought
If the same script today gives a healthy IoU on the same kmodel and same images, then either (a) the script was edited in place after the OLD run and the OLD version was buggy, or (b) something about the run-time environment changed.
What we tried
Cross-checked everything an OLD-vs-NEW comparison could hinge on:
  • kmodel file hash (sha256 57384B8F…) — unchanged
  • label files — byte-identical between my_dataset/train/labels/ and IR-2026-05-07-18-52/labels/ (verified by diff)
  • image bytes — md5sums identical across mounts
  • Categories: dataset's classes.txt says 0=black, 1=silver but the eval script defaults to --categories silver black. IoU is matched on the integer index, so this only mis-labels the CSV's gt_cls column — it doesn't drive IoU to zero.
What we found
The OLD eval had used --images-dir /datasets/my_dataset/train/images; the fresh re-run we did first used the original IR-2026-05-07-18-52 directory. Different random.Random(42).sample selections, hence a zero overlap between the two 50-image samples — but the population is the same images on disk. We ran the eval again with the OLD command's exact --images-dir + --labels-dir + --limit 50, hit the same num_gt = 76 as the OLD eval, and got back avg_best_iou = 0.794, not 0.0.
The verdict
pc_eval_yolov8.py as it sits in the repo today is correct. The version that produced the OLD recall = 0.0 was a buggy earlier file that has been overwritten in place — its on-disk timestamp now reads 2026-05-19 00:33, before the eval ran, but content is no longer recoverable. No backups in __pycache__, no git history for the file (it was untracked when the OLD eval ran), no shadow copies. We can't recover the bug, but we proved it isn't in the current code.

One persistent cosmetic bug remains in the current script: the gt_cls column in reports/repro_pceval/*.csv shows the wrong class name because of the categories-order mismatch. IoU and recall are unaffected.

Phase 7Device deploy and the "silver 638.50" surprise

When the kmodel started running on hardware it printed nonsense scores.

With i16-activation kmodel validated on PC, we ported the single-image inference path to the K230D. The first version of src/deploy/det_image_yolov8.py was a clone of the AnchorBaseDet image script, with the post-process swapped from aicube.anchorbasedet_post_process to aicube.anchorfreedet_post_process (which already lived inside the live script).

The user ran it. The annotated output showed two boxes pinned in the corners of the image with labels like:

silver  638.50
black    24.94

A confidence "score" of 638 is impossible for a sigmoid output that lives in [0, 1]. But 638 is a plausible pixel coordinate in a 640-wide image. The aicube helper was reading the model's bbox channels and printing them as class scores.

Phase 8A preprocessing pivot we got wrong

Honest about a mistake we made and undid.

While diagnosing the device output, we briefly convinced ourselves that the live script's preprocessing didn't match calibration. The live script set the sensor to Sensor.GRAYSCALE, called img.histeq() on every frame, and replicated the single grayscale plane to three channels — while we believed calibration used color RGB images via cv2.imread.

We rewrote the live script to use Sensor.RGB888 and disable histeq, and we put a note in YOLOV8_K230_QUANT_DIAGNOSIS.md saying the device path had a calibration mismatch.

The user pushed back: the test image they had loaded onto the board was a grayscale, already-histeq'd JPG — the standard format of the training set. That was a clue we hadn't accounted for. We opened a few calibration JPGs and split them into channels:

data/calibration_74/003a746b-1s1b_0216.jpg
  shape=(480,640,3)  B==G=1  G==R=1  pixel=[50,50,50]
data/calibration_74/072ce14b-0s1b_0109.jpg
  shape=(480,640,3)  B==G=1  G==R=1  pixel=[25,25,25]

Every JPG in calibration_74/ is a grayscale-histeq image saved as a 3-channel JPG with all three planes equal. The training pipeline reads them as "RGB" but the data is grayscale. So the original live script was actually correct: grayscale sensor + histeq + 3-channel replicate reproduces the calibration distribution exactly.

We reverted the live script to its original sensor + preprocessing configuration and rewrote the relevant paragraph in the diagnosis report. The preprocessing mismatch we had hypothesized did not exist.

Calibration distribution is determined by the bytes inside the JPGs, not by the dataloader's docstring or by intuition about what "RGB" means.

Phase 9Replacing aicube with pure-python decode

The real reason the device printed "silver 638.50".

With preprocessing ruled out we looked at the postprocess. The Ultralytics YOLOv8 export ends with two operations: a Concat of already-decoded bounding-box centers, widths, and heights, and a Sigmoid on the per-class scores. The output is a single tensor of shape (1, 4+nc, 6300) in channel-first layout:

channel 0 — cx (in model pixel space, 0..640)
channel 1 — cy
channel 2 — w
channel 3 — h
channel 4 — class 0 score (sigmoided, 0..1)
channel 5 — class 1 score

The 6300 columns are 6300 candidate anchors — the union of grid cells across the three strides 8/16/32 (80·60 + 40·30 + 20·15 = 6300).

aicube.anchorfreedet_post_process is a helper from Canaan's YOLOv8 reference, but it's designed for a different ONNX output: three separate per-stride raw feature maps, on which it performs its own Distribution Focal Loss decoding and grid arithmetic. Feeding it our single already-decoded tensor — even three times to satisfy its three-input signature — produces garbage because it's looking for raw logits where we have decoded values in pixel space. The "score" the helper printed in the screenshot (638.50) is a cx for the last anchor of the stride-32 grid (640 − ε).

The fix is to bypass the vendor helper and decode the tensor ourselves, byte-for-byte the same as the PC simulator path (src/eval/pc_eval_yolov8.py):

  1. For each of the 6300 anchors, take the argmax over channels 4 and 5 — that's the class, that's the score.
  2. If score < CONF_THRESHOLD, drop the anchor.
  3. Otherwise convert (cx, cy, w, h) to (x1, y1, x2, y2).
  4. Run per-class greedy non-maximum suppression.
  5. Map surviving box corners back from letterbox coordinates to the original image with unletterbox_box.

We wrote this in pure Python on top of ulab.numpy in src/deploy/yolov8_decode.py. At CONF_THRESHOLD = 0.30 the inner loop short-circuits on the cls compare before touching the bbox arithmetic, so the 6300-anchor decode finishes in well under a second on the K230.

Phase 10Modularization

One decoder, two scripts.

The image script and the live script needed the same decoder, NMS, and unletterbox helpers. Rather than duplicate them, we extracted the helpers into a single shared module:

  • src/deploy/yolov8_decode.py — pure-python decode + NMS + unletterbox + IoU.
  • det_image_yolov8.py — loads a JPG, runs gray → histeq → 3-channel replicate → letterbox → KPU → decode → NMS → unletterbox → draw → save.
  • det_live_xy_yolov8.py — same pipeline against the sensor in a loop, plus the UART packet emission to the Teensy.

Open threads

  • The exact bug in the earlier pc_eval_yolov8.py is unrecoverable. We can prove the current file works; we can't prove what was wrong with the version that produced recall = 0.
  • batch_export.py's deploy_config writer doesn't know about YOLOv8. It hardcodes the AnchorBase template, so YOLOv8 exports get model_type = "AnchorBaseDet" and categories = [black, silver] (wrong order). We hand-edited the one config we cared about. The fix is small but out of scope this session.
  • Pure-python decode latency on K230 hasn't been measured on hardware yet. 6300 anchors with a Python loop should be fast enough at conf ≥ 0.3 because most iterations short- circuit on the cls compare, but real-world FPS needs a stopwatch. If it turns out to be a bottleneck, vectorizing with ulab.numpy is the obvious next step.
  • The cosmetic gt_cls column mislabel in pc_eval_yolov8.py output should get fixed if anyone reads CSVs by class name.

Lessons

  • Trust on-disk eval summaries less than re-runs. JSON files don't carry the code version that produced them; if a number surprises you, re-run the eval before drawing any conclusion.
  • Verify the channel layout and shape contract of every vendor post-process helper before plugging it in. Both aicube.anchorbasedet_post_process and aicube.anchorfreedet_post_process exist; they look almost identical from the call site; they have completely different assumptions about what the model returns.
  • Calibration distribution is determined by the bytes inside the JPGs, not by the dataloader's docstring. Check with cv2.split + numpy.array_equal.
  • Score saturation looks like a model failure but is a quantization-arithmetic failure. The detector usually still knows where things are — it's the last-layer activation that gets crushed to one of 256 bins. Promoting that single layer to int16 is cheap and usually sufficient.
  • Pivots are part of the work; document them honestly. The Phase 8 detour was a real cost that almost shipped a broken live script. Writing it down so the next person doesn't repeat it is worth the embarrassment.
